# AI Model Configuration Wizard Design

## Summary

Simplify daily AI model and route administration by making Model Center the single primary entry point. Add a guided workflow that configures a product model, provider connection, route credential, pricing, connectivity test, and publication without requiring the administrator to move between Template Library, Provider Connections, and Model Center.

The existing AI Gateway database model, tenant boundaries, plugin manifests, route runtime, and advanced administration APIs remain intact. Provider Connections and Template Library remain available as advanced tools.

## Goals

- Let an administrator configure and publish the first usable route for a product model without leaving Model Center.
- Support built-in provider templates and custom OpenAI-compatible endpoints.
- Hide route implementation details during the common path while preserving advanced editing.
- Require every route to explicitly bind a credential, whether newly created or deliberately reused.
- Require complete pricing and a successful live route test before a route can become active.
- Preserve existing route keys, installed configurations, runtime behavior, and tenant isolation.

## Non-Goals

- Removing tenant-aware data ownership or converting application data to global scope.
- Replacing the AI Gateway tables with one combined configuration table.
- Removing Provider Connections or Template Library.
- Automatically importing or rotating provider credentials.
- Automatically synchronizing upstream prices, exchange rates, or profit margins.
- Creating all possible provider routes when a model is first configured.

## Chosen Approach

Extend the existing Model Center with a configuration wizard and a narrowly scoped backend draft orchestration API. The orchestration API performs related database writes transactionally. Live provider testing remains a separate request so an external call never holds a database transaction open.

This approach retains the existing normalized records and runtime contracts while removing their complexity from the normal administrator workflow.

## Information Architecture

Model Center becomes the daily management surface and contains:

- A primary `Configure model` command.
- Product model rows showing modality, default route, usable route count, price, health, and publication status.
- A product model detail view showing all routes and their default, health, credential, connection, upstream model, price, and last test state.
- Route commands for test, set default, disable, duplicate as a backup route, and advanced edit.
- A secondary `Advanced settings` entry linking to Provider Connections and Template Library.

Template Library remains an initialization and inspection tool. Provider Connections remains the place for advanced provider resource and connection management. Neither is required for the guided common path.

## Wizard Flow

### Step 1: Select Model

The administrator selects a built-in model template or `Custom OpenAI-compatible`.

Built-in templates provide provider kind, supported modality, model family, UI schema, default endpoint behavior, and pricing defaults. The custom option exposes the minimum compatible endpoint fields needed to construct a valid route.

### Step 2: Service Connection

The administrator confirms the provider, Base URL, and environment. Template defaults are prefilled. Existing compatible connections may be selected, or a new connection may be created.

Provider describes the vendor/runtime adapter. Connection describes the reusable Base URL and environment resource. A connection does not implicitly determine the route credential.

### Step 3: Primary Route and Credential

The administrator confirms a friendly route label and upstream model, then explicitly chooses one credential action:

- `Create credential`: enter a credential name and API key.
- `Select existing credential`: choose a compatible credential filtered by provider.

Existing credentials display only name, status, fingerprint suffix, and last-used time. Secret plaintext is never returned.

Every route stores its own `credential_id`. Routes under the same provider or product model may use different credentials. Multiple routes may deliberately share one credential.

Route key, API mode, request path, timeout, and raw request configuration are generated by the template and hidden under advanced configuration.

### Step 4: Pricing

The template prefills the expected credit price. The administrator may adjust it before saving. Missing or invalid pricing prevents activation. Existing fail-closed `PRICING_NOT_FOUND` runtime behavior remains unchanged.

Automatic upstream price synchronization, currency conversion, and margin calculation are outside this scope.

### Step 5: Test and Publish

The final step presents a configuration summary and supports:

- `Save draft`: persist a non-runnable configuration.
- `Test route`: perform a real provider connectivity/generation test.
- `Enable and publish`: available only after the current saved configuration passes testing.

After publication, the administrator returns to the product model detail page. A completion action offers `Add backup route`.

## Backup Routes

The first pass creates one primary route. Additional routes are added later by duplicating an existing route or starting a route-specific wizard.

Duplication may copy provider, connection, endpoint settings, upstream model, pricing, and request configuration. Credential selection is deliberately reset to `unconfirmed`; the administrator must choose an existing credential or create a new one before saving the duplicated route.

This prevents accidental secret inheritance while still allowing explicit credential reuse.

## Data Model and Scope

No AI Gateway ownership columns are removed. Existing `tenant_id` behavior remains unchanged.

The wizard uses the existing entities:

- `ai_providers`
- `ai_models`
- `ai_provider_connections`
- `api_credentials`
- `tenant_ai_plugin_installs`
- `ai_model_catalog`
- `ai_routes`
- `model_pricing`
- `ai_route_health_checks`

The backend determines the correct existing platform or tenant scope using the same authorization and scope rules as the current Model Center APIs. The wizard must not allow a tenant-scoped connection or credential to be attached to a platform route when existing API rules forbid it.

## Save and Publish Data Flow

The first four steps keep transient values in React memory only. They do not put secrets in localStorage, IndexedDB, URLs, analytics, or draft graph JSON.

On `Save draft`, a backend orchestration endpoint performs one database transaction:

1. Resolve or create the provider supported by the selected template.
2. Resolve or create the provider connection.
3. Create a new encrypted credential or validate the explicitly selected credential.
4. Install or associate the plugin package and product catalog model.
5. Create or update the primary route in a non-active state.
6. Persist pricing and the proposed default route relationship.
7. Return sanitized identifiers, labels, status, and credential metadata.

Any database failure rolls back the transaction. The response never contains credential plaintext or encrypted credential fields.

Live testing occurs after the draft transaction commits. A successful test records the health result. Publication then performs a short transaction that verifies the saved configuration has not changed since the successful test, marks the route and product model active, and assigns the default route. If relevant fields changed after testing, another test is required.

## State Model

- `Unsaved`: wizard state exists only in memory.
- `Draft`: database records exist but are not visible in canvas model selectors.
- `Ready for test`: all required connection, credential, upstream model, and pricing fields are complete.
- `Test failed`: draft remains editable and includes a sanitized failure summary.
- `Active`: latest saved configuration passed testing and is published to canvas selectors.
- `Inactive`: historical configuration remains, but new jobs cannot select it.

Closing a wizard with unsaved changes prompts the administrator to discard or save a draft.

## Credential Lifecycle

- New API key plaintext is accepted only during credential creation or explicit rotation.
- Frontend responses expose sanitized metadata only.
- Updating one route's credential binding does not affect other routes.
- Rotating a shared credential affects every route that references that credential and must display the impacted routes before confirmation.
- A credential referenced by routes cannot be deleted.
- A referenced credential may be disabled, but active routes cannot be published with a disabled credential.
- Logs, audit metadata, screenshots, test summaries, and error responses must not contain API keys, encrypted secrets, nonces, auth tags, or Authorization headers.

## Error Handling

- Validation errors identify the wizard step and field that needs correction.
- Provider test failures preserve the draft and return a sanitized upstream error code/message plus request ID when available.
- Authentication failures suggest checking the selected credential without revealing request headers.
- Endpoint and model errors navigate back to the connection or primary route step.
- Pricing errors navigate back to the pricing step and block activation.
- Database orchestration failures create no partial draft records.
- Duplicate route keys are resolved before creation; existing saved route keys are never silently renamed.
- Concurrent edits use the existing revision/update safeguards where available, or an `updatedAt` precondition in the new orchestration endpoint.

## Advanced Configuration

Built-in templates normally hide:

- Route key
- API mode
- Request and polling paths
- Timeout
- Raw request configuration
- Priority, weight, and fallback group

An `Advanced configuration` section exposes these values to authorized administrators. Existing routes remain editable through the current detailed interfaces. Stable route keys are preserved once saved.

## Permissions and Audit

The wizard uses the existing provider/model administration permission checks. It is not exposed to normal creator roles.

Audit events cover draft creation, credential binding, route test, publication, default-route changes, disabling, and credential rotation. Audit metadata identifies resource IDs and sanitized names but excludes secrets.

## Testing

### Frontend

- Complete the five-step built-in template flow without leaving Model Center.
- Complete the custom OpenAI-compatible flow.
- Validate step navigation, unsaved-close confirmation, draft restoration from server data, and responsive layout.
- Verify missing credentials, upstream model, or pricing block testing/publication.
- Verify credential creation and existing-credential selection are mutually exclusive.
- Verify duplicated routes require credential reconfirmation.
- Verify secrets never appear after submission or in rendered error details.

### API and Database

- Verify the draft orchestration transaction creates all required records or none.
- Verify provider, connection, and credential scope constraints.
- Verify same-provider routes can bind different credentials.
- Verify multiple routes can share one credential explicitly.
- Verify referenced credentials cannot be deleted.
- Verify active routes cannot use disabled credentials or missing pricing.
- Verify successful tests apply only to the tested saved revision.
- Verify existing route keys and legacy installed configurations remain unchanged.

### Runtime

- Verify only active, successfully published routes appear in model catalogs used by canvas selectors.
- Verify default-route selection and fallback behavior remain compatible.
- Verify `PRICING_NOT_FOUND` continues to fail closed.
- Verify runtime credential resolution uses the credential bound to the selected route.

### Required Validation

- `npm run build`
- `npm run test --workspace @aigc-flow/api`
- `npm run test --workspace @aigc-flow/ai-gateway-core`
- Relevant focused frontend tests for Model Center and the wizard
- Relevant database tests if schema or transaction helpers change

## Acceptance Criteria

- An authorized administrator can configure, test, and publish a first model route entirely within Model Center.
- Built-in templates prefill endpoint behavior and pricing; custom OpenAI-compatible endpoints remain supported.
- The common path does not require manual Route Key, API Mode, or request-path entry.
- Every route explicitly binds a newly created or selected credential.
- Routes under the same provider or product model can use distinct credentials.
- Multiple routes can deliberately reuse one credential.
- Duplicated routes cannot be saved until credential binding is reconfirmed.
- Missing credential, upstream model, or pricing prevents activation.
- A failed live test leaves an editable draft and never publishes the route.
- Only a successful test of the current saved revision permits publication.
- Existing routes, stable route keys, tenant isolation, and canvas behavior remain compatible.
- No provider secret is exposed to frontend state after submission, logs, audit metadata, errors, canvas node data, or flow drafts.
