# 充值体验优化设计

日期：2026-08-18

状态：待用户评审

## 目标

将充值从 `/billing` 右侧的隐蔽面板，升级为可从任意创作场景触达的“充值商品选择 + 快捷支付”体验，同时保持当前 v2 的一次性购买、个人钱包、服务端支付和账单模型。

用户必须能快速理解：

- 当前有多少可用积分；
- 每个套餐到账多少积分、多少钱、有效期多久；
- 充值是一次性购买，不自动续费；
- 支付后积分何时到账，以及失败时如何重试。

## 产品边界

当前充值是一次性购买固定套餐，不支持自动续费，不新增自定义金额。

现有后端支付接口继续作为唯一支付入口：

- `GET /api/v2/billing/recharge-plans`
- `POST /api/v2/billing/payment/create-checkout`
- `GET /api/v2/billing/payments/:paymentId`

前端不直接修改余额，支付完成后继续通过账单摘要接口刷新钱包状态。

## 方案选择

### 推荐方案：全局快捷充值弹窗 + 完整账单页

顶部长期展示“积分余额 + 充值”入口。点击后在当前页面打开充值弹窗，不打断画布或工作台上下文。`/billing` 负责完整的余额、充值、支付、兑换码、充值记录和消耗明细管理。

### 未采用的方案

- 只优化 `/billing`：改动小，但用户仍需离开当前工作流。
- 只在余额不足时弹窗：正常状态下入口仍然隐蔽，无法支持主动充值。
- 订阅式套餐：与现有支付接口和产品规则不一致，会造成自动续费误解。

## 信息架构

### 全局入口

在 `WorkspaceShell` 的账户区域展示：

```txt
积分 1,280    充值
```

充值按钮使用高对比度主按钮样式，余额数字保持可扫描但不抢过主要导航。

账户下拉菜单中的余额卡增加“立即充值”按钮。顶部导航中的“账单充值”改为“账单”，因为充值已经有全局快捷入口。

### 创作场景入口

画布和工作台的生成操作附近展示预估费用与当前余额：

```txt
预计消耗 24 积分，当前可用 1,280 积分
```

低余额状态展示：

```txt
预计消耗 24 积分，当前可用 8 积分
余额不足，充值后继续
```

点击后打开同一个充值弹窗，并保留当前生成参数。充值完成后不自动重复提交任务，用户明确点击原来的生成操作后再执行。

### `/billing` 页面

页面首屏主体顺序调整为：

1. 页面标题、一次性购买声明和余额摘要；
2. 充值套餐区域；
3. 支付状态；
4. 兑换码；
5. 充值记录和积分消耗明细。

充值套餐不再放在当前右侧窄栏中。账单活动表可以在套餐区域下方全宽展示，或在桌面端与明细区域形成明确的上下层级。

## 充值商品页

### 页面标题

```txt
充值积分
一次购买，立即到账，不自动续费
积分可用于图片、视频和工作流生成
```

### 分类

第一阶段只显示“通用积分”一类，不创建无实际数据支持的空 tab。后续可以增加“活动赠送”“兑换码”“企业充值”，但分类必须由服务端套餐数据驱动。

### 套餐卡片

桌面端 3 列，移动端单列。首屏优先展示 3 个套餐，更多套餐放在下方或折叠区域。

每张卡片显示：

- 套餐名称，例如“入门创作”“项目启动”“高频创作”；
- 到账总积分；
- 基础积分与赠送积分（若数据可用）；
- 实付金额；
- 折算提示，例如“每 100 积分约 ¥1.20”；
- 有效期；
- 面向用户的用途描述；
- “立即充值”按钮。

推荐套餐使用青色边框或背景、明确的“推荐”标签和填充式 CTA；其他套餐使用描边式 CTA。推荐逻辑由服务端或稳定的排序字段提供，不能由前端按价格猜测。

### 数据兼容策略

第一阶段直接使用现有 `RechargePlan` 字段：

- `name`
- `amountCents`
- `credits`
- `validityDays`
- `sortOrder`

缺少赠送拆分、原价和标签时，不显示虚构的折扣文案，而只展示到账积分、价格和有效期。

第二阶段可扩展套餐展示字段：

```ts
{
  category: "general",
  baseCredits: 7500,
  bonusCredits: 3750,
  badge: "首充加赠 50%",
  recommended: true,
  originalAmountCents: 60000,
  featureText: "适合日常图像与视频生成"
}
```

赠送积分必须由服务端计入真实钱包入账，前端不得自行计算或伪造。

## 快捷充值弹窗

弹窗包含两个状态。

### 选择套餐

- 当前可用积分；
- 一次性购买、不自动续费说明；
- 3 个主要套餐卡片；
- 有效期和到账说明；
- 点击套餐后创建支付订单。

### 支付中

- 订单金额；
- 到账积分；
- 二维码或支付跳转；
- 当前支付状态；
- 订单过期提示；
- 支付成功、失败、取消和退款状态。

支付成功后展示：

```txt
充值成功
+12,000 积分已到账
当前可用积分 13,280
```

提供“继续创作”和“查看账单”两个动作。失败或取消时提供“重新支付”和“返回套餐”。不在支付成功后自动提交原本被余额拦截的生成任务。

现有 `paymentId` URL 参数和轮询机制可以继续使用，但支付状态应该集中显示在弹窗中；`/billing` 仍保留最近一次支付状态，便于用户刷新或返回后恢复。

## 响应式与视觉方向

- 保持 TapNow 深色背景；
- 使用青色作为充值、推荐和成功状态的强调色；
- 套餐卡片采用稳定宽度和固定 CTA 区域，避免标签或长文案导致布局跳动；
- 桌面端使用 3 列网格，移动端单列；
- 移动端优先让套餐价格、到账积分和 CTA 位于首屏，支付二维码使用现有跳转策略；
- 不使用订阅式“月付/年付”文案，不添加没有真实功能的装饰性分类。

## 错误与边界

- 套餐列表加载失败：显示可重试状态，不渲染空白购买按钮；
- 支付创建失败：保留当前选择，允许重新创建订单；
- 支付超时：提示订单状态可能延迟，继续轮询或进入账单查询；
- 支付成功但摘要刷新失败：以支付状态为准，显示“到账状态同步中”，随后可手动刷新；
- 订单过期或取消：允许返回套餐重新选择；
- 余额不足：在预估费用后拦截，不创建工作流、不预留积分；
- 缺少价格或套餐配置异常：不显示免费执行或虚假折扣，保持服务端失败关闭规则。

## 分阶段交付

### 第一阶段：不改数据库

- 全局余额和充值入口；
- 快捷充值弹窗；
- `/billing` 首屏重排；
- 3 列套餐卡片和推荐视觉；
- 支付状态集中展示；
- 低余额提示；
- 移动端适配；
- 复用现有支付和轮询 API。

### 第二阶段：套餐展示能力增强

- 套餐分类；
- 基础积分与赠送积分；
- 原价、折扣和标签；
- 推荐标记；
- 用途和权益说明；
- 管理后台可配置展示内容。

## 验收指标

- 从任意页面打开充值弹窗的成功率；
- 打开充值到创建订单的平均耗时；
- 套餐选择到支付的转化率；
- 支付成功率；
- 余额不足后重新发起生成的完成率；
- 充值页退出率；
- 支付成功后钱包摘要刷新成功率。

## 不在本次范围内

- 自动续费和订阅；
- 自定义充值金额；
- 新支付渠道；
- 前端直接修改余额；
- 用 localStorage 或 IndexedDB 保存权威充值状态；
- 把兑换码、管理员充值和充值套餐混成同一种商品卡片。
